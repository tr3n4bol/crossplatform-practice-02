# Материалы к защите

## Устройство официального примера Calculator

Для задания я выбрал Calculator из официальной коллекции Microsoft dotnet/maui-samples. Это небольшой проект .NET MAUI 10, который удобно читать без сборки. На скриншоте VS Code видны общая часть, платформенные каталоги и файл Calculator.csproj. Я проверял файлы одной зафиксированной ревизии, чтобы анализ можно было повторить.

В общей части Calculator.cs выполняет четыре арифметические операции. MainPage.xaml задаёт расположение кнопок и полей результата, а MainPage.xaml.cs содержит обработчики ввода и вычислений. При нажатии кнопки обработчик обновляет состояние страницы, вызывает Calculator.Calculate и выводит результат. MauiProgram.cs собирает приложение и регистрирует шрифты. Один и тот же исходный код этих файлов используется для поддерживаемых целей.

Граница платформы проходит через каталог Platforms и условия в Calculator.csproj. В Android есть MainActivity, MainApplication и AndroidManifest.xml. В Windows — свой App.xaml.cs, класс MauiWinUIApplication и манифесты. При этом обе платформы подключают общую конфигурацию MAUI. В конфигурации проекта есть цели Android, iOS и Mac Catalyst, а цель Windows добавляется на хосте Windows. Tizen присутствует в исходниках, но для него нужно отдельно включить целевую платформу.

В общем коде я не обнаружил прямых вызовов API конкретной ОС. По непустым строкам C# и XAML, включая стили, примерно 87% относятся к общей части. Этот процент характеризует только выбранный образец. Приложение переносится благодаря общему фреймворку и его платформенным реализациям. При переносе на Astra Linux или «Аврору» общую арифметику можно переиспользовать как отдельный модуль. Интерфейс и упаковку пришлось бы адаптировать под доступный там стек. Пример также показывает, что проверять стоит не только наличие платформенной цели, но и поведение ввода на локалях с разными десятичными разделителями.

## Выбор фреймворка для варианта 3

Для корпоративного приложения на Windows и Android выбираю .NET MAUI. В этом сценарии есть команда C# и инфраструктура Microsoft, а требования к запуску на Linux и в браузере не заданы. Оба фреймворка поддерживают нужные платформы. Microsoft публикует требования к Windows и Android и документирует сборку для каждой из них [24, 29, 30]. Это позволяет сверить парк устройств и заранее определить, где собирать и подписывать пакеты. Версию фреймворка для внедрения следует закрепить после проверки требований ИТ-службы к срокам поддержки.

Второй аргумент связан с устройством интерфейса. В MAUI можно использовать общие страницы и модели, а handlers связывают контролы с представлениями Windows и Android [25]. Для типовых форм, списков и ввода это даёт предсказуемую отправную точку. Поведение клавиатуры, фокуса и доступности всё равно нужно проверить на обеих ОС. Опыт C# пригодится в работе с общей логикой, хотя XAML и нюансы каждого пакета потребуют отдельной подготовки.

Третий аргумент — доставка обновлений. Для Windows можно использовать подписанный MSIX, для Android — подписанный пакет подходящего формата. Если организация уже использует Intune, приложения обеих платформ можно вести в одной системе управления [29–31]. До выбора канала стоит проверить, какие устройства управляются централизованно и кто отвечает за ключи подписи.

Uno Platform я бы рассматривал при наличии значительного объёма готового WinUI XAML или требования к Linux либо вебу. Его Skia-режим полезен для согласованного внешнего вида на разных платформах [26, 27]. Для исходного сценария эти возможности не определяют выбор. На пилоте я сравнил бы время холодного запуска, размер подписанных пакетов и отзывчивость типовой формы на одном Windows-компьютере и одном Android-устройстве.
